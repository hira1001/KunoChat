# V0.6.0 Hybrid Delivery Detailed Design

## 1. Module Boundaries

### New Modules

| Module | Responsibility |
| --- | --- |
| `src/features/delivery/deliveryStrategy.ts` | Pure route decision logic |
| `src/features/delivery/deliveryTypes.ts` | Shared delivery/outbox/provider types |
| `src/features/delivery/deliveryRouter.ts` | Orchestrates route choice, transport call, retry, status update |
| `src/features/delivery/outboxStore.ts` | Durable local outbox facade; production implementation must persist before send |
| `src/features/delivery/deliveryWorker.ts` | Starts delivery work on send, app start, reconnect, route discovery, and retry timers |
| `src/features/delivery/recipientIdentityStore.ts` | Conversation-scoped peer identity, trust, and mailbox metadata |
| `src/features/delivery/transports/p2pTransport.ts` | Adapter over current `sendRealtimeMessage` path |
| `src/features/delivery/transports/relayTransport.ts` | Ably/Pusher provider-neutral relay adapter |
| `src/features/delivery/transports/storeForwardTransport.ts` | Worker/R2 store-and-forward adapter |
| `src/features/delivery/cryptoEnvelope.ts` | Envelope encryption/decryption and ACK authentication |

### Existing Modules to Integrate

| Existing Module | Change |
| --- | --- |
| `src/app/App.tsx` | Calls delivery router instead of directly calling `sendRealtimeMessage` |
| `src/features/chat/chatStore.ts` | Owns visible message state; receives delivery status updates; no provider SDK imports |
| `src/features/realtime/realtimeClient.ts` | Remains P2P realtime client |
| `src/features/native/platformAdapter.ts` | Supplies native file sources and future secure storage helpers |
| `src/features/storage/db.ts` | Candidate for durable outbox persistence |

### Hard Invariants

- `sendDraft` or its replacement must never leave a known-recipient message idle; it must enqueue durable work and kick the delivery worker.
- `messageId`, transfer ids, envelope ids, outbox ids, and provider idempotency keys must be generated with `crypto.randomUUID()` or equivalent random entropy. Timestamp-only ids are forbidden.
- A queued item may flush only when `conversationId` and `recipientDeviceId` match the active delivery route.
- Device trust is per conversation/recipient. A global `settings.trustedPeer` must not be used to validate every conversation.
- Provider secrets must never be bundled into the desktop client.

## 2. Core Types

### DeliveryEnvelope

```ts
export type DeliveryEnvelope = {
  version: 1;
  envelopeId: string;
  messageId: string;
  conversationId: string;
  senderDeviceId: string;
  senderPublicKey: string;
  recipientDeviceIdHash: string;
  createdAt: number;
  expiresAt: number;
  payloadKind: "control" | "text" | "image" | "file";
  payloadSizeClass: "tiny" | "small" | "medium" | "large";
  ciphertext: string;
  nonce: string;
  keyId: string;
  signature: string;
  attachmentRefs?: EncryptedAttachmentRef[];
};
```

Rules:

- `ciphertext` is base64url encoded encrypted JSON.
- Plaintext body, filename, caption, and MIME should not appear outside ciphertext where avoidable.
- `recipientDeviceIdHash` is stable enough for routing but not a raw public identifier.
- `expiresAt` is mandatory.
- `signature` signs the canonical envelope fields excluding `signature` and must be verified before decrypt.
- `envelopeId` and `messageId` are UUID-based idempotency inputs.

### RecipientIdentity

```ts
export type RecipientIdentity = {
  id: string;
  conversationId: string;
  peerId?: string;
  peerHint?: string;
  displayName: string;
  publicKey?: string;
  fingerprint?: string;
  trustedAt?: number;
  mailboxIdHash?: string;
  relayChannelId?: string;
  lastVerifiedAt?: number;
  createdAt: number;
  updatedAt: number;
};
```

Rules:

- `RecipientIdentity` replaces global peer trust for delivery decisions.
- `publicKey` and `fingerprint` are scoped to the conversation.
- When a received identity differs from the trusted identity for that conversation, only that conversation fails verification.
- Unknown conversations may use trust-on-first-use, but the first trusted key must be stored on the recipient identity record.

### OutboxRecord

```ts
export type OutboxRecord = {
  id: string;
  messageId: string;
  conversationId: string;
  recipientIdentityId: string;
  recipientDeviceId?: string;
  recipientPeerId?: string;
  recipientPeerHint?: string;
  payloadKind: DeliveryPayloadKind;
  sizeBytes: number;
  route: DeliveryRoute;
  status:
    | "local_queued"
    | "p2p_sending"
    | "relay_accepted"
    | "store_accepted"
    | "peer_delivered"
    | "read"
    | "failed_retryable"
    | "failed_final"
    | "cancelled";
  attempts: number;
  lastAttemptAt?: number;
  nextRetryAt?: number;
  expiresAt: number;
  providerMessageId?: string;
  idempotencyKey: string;
  errorCode?: string;
  errorMessage?: string;
  createdAt: number;
  updatedAt: number;
};
```

Rules:

- One visible chat message can have one outbox record for text.
- A bundle can have one message-level outbox record plus per-attachment transfer records.
- `messageId` is idempotency key across all transports.
- `status` is more detailed than current `ChatMessage.status`.
- `recipientIdentityId` is required before remote delivery. If unresolved, the record remains local and route discovery starts.
- `idempotencyKey` is UUID-based and stable across retries.

### DeliveryTransport

## 3. Delivery Router Algorithm

```ts
async function send(message: ChatMessage) {
  const recipient = await recipientIdentityStore.resolveForConversation(message.conversationId);
  const outbox = await outboxStore.createOrUpdate(message, recipient);
  deliveryWorker.kick("send-requested");
}

async function processOutboxRecord(outbox: OutboxRecord) {
  const message = await chatMessageRepository.get(outbox.messageId);
  const recipient = await recipientIdentityStore.get(outbox.recipientIdentityId);
  if (!message || !recipient) {
    await outboxStore.markRetryableFailure(outbox.id, "missing_local_context");
    return;
  }
  if (message.conversationId !== outbox.conversationId || recipient.id !== outbox.recipientIdentityId) {
    await outboxStore.markFinalFailure(outbox.id, "recipient_context_mismatch");
    return;
  }

  const context = await buildDeliveryContext(message, recipient);
  const decision = chooseDeliveryRoute(context);
  await outboxStore.markRoute(outbox.id, decision.route);
  await chatStore.applyDeliveryDecision(outbox.messageId, decision);

  if (decision.startP2PInBackground) {
    p2pConnector.ensureConnecting(outbox.conversationId, recipient);
  }

  switch (decision.route) {
    case "p2p":
      return sendP2P(message, outbox, recipient);
    case "relay":
      return sendRelay(message, outbox, recipient);
    case "store_forward":
      return storeForward(message, outbox, recipient);
    case "local_queue":
      return scheduleRetry(outbox, decision.retryAfterMs);
  }
}
```

Important:

- Local message creation remains in chat store before router send begins.
- Outbox persistence happens before provider or P2P send attempts.
- `send(message)` only enqueues and kicks the worker; worker processing is re-entrant and idempotent.
- Worker processing reloads message and recipient context from durable/local stores before sending.
- Router must not create duplicate visible messages.
- Router must check stored conversation/recipient identity before flushing queued records.
- P2P and relay may race in later versions, but v0.6.0 uses deterministic route choice to avoid duplicate complexity.

## 3.1 Delivery Worker Triggers

The delivery worker must run when:

- the user sends a draft,
- the app starts,
- a retry timer becomes due,
- P2P status changes to connected,
- relay/store provider configuration changes,
- route discovery finds a known peer,
- a conversation is selected,
- a queued record is manually retried.

The worker must not require the pairing screen to be visible. If a known recipient has `peerHint`, mailbox metadata, or relay metadata, route discovery starts in the background.

Worker locking rules:

- Only one processing loop may own an outbox record at a time.
- Use `attempts`, `lastAttemptAt`, and a transient in-process lock to avoid parallel duplicate sends.
- If the process crashes after provider acceptance but before local status update, retry must use the same `idempotencyKey`.

## 6. Persistence Design

### v0.6.0 Minimum

- Persist outbox records in the existing app persistence layer or SQLite if already stable.
- Persist provider ids, retry counters, route, detailed delivery status, and expiry.
- Do not persist raw `File` objects; persist path-backed file references only when available.

### Future SQLite Table

Persistence requirements:

- In-memory outbox is allowed only in unit tests and throwaway prototypes.
- Production v0.6.0 must use durable persistence before any network operation.
- Migration must create `recipient_identity` records before creating remote-eligible outbox records.

## 7. Provider API Contracts

### Relay Provider

Required operations:

- `requestRelayToken(scope): Promise<RelayToken>`
- `publishEnvelope(envelope, token, idempotencyKey): Promise<RelayAccepted>`
- `subscribe(deviceIdHash, token, handler): Promise<Unsubscribe>`
- `publishAck(ack, token): Promise<void>`

Required properties:

- At-least-once delivery is acceptable.
- Receiver must deduplicate by `messageId`.
- Relay provider ACK is not peer delivery.
- Payload must be encrypted before publish.
- Publish tokens are scoped to a sender, recipient mailbox/channel, operation, and short expiry.
- Subscribe tokens are scoped to one recipient mailbox/channel and short expiry.
- Relay rejects envelopes whose sender signature does not verify against the claimed sender key.

### Store-Forward Provider

Required operations:

- `requestStoreToken(scope): Promise<StoreToken>`
- `putEnvelope(envelope, token, idempotencyKey): Promise<StoreAccepted>`
- `listPending(deviceIdHash, token): Promise<DeliveryEnvelope[]>`
- `ackDelivered(messageId, ack, token): Promise<void>`
- `deleteEnvelope(messageId, token): Promise<void>`
- `putEncryptedObject(ref, bytes, token, idempotencyKey): Promise<ObjectAccepted>`
- `getEncryptedObject(ref, token): Promise<ReadableStream>`

Required properties:

- TTL must be set server-side.
- Store must reject expired or oversized payloads.
- API must be idempotent by `messageId`.
- Store validates sender signatures before accepting envelopes.
- Store tokens must be scoped to mailbox/object prefixes; broad account tokens are not allowed in the client.

## 8. Encryption and ACK Design

### Envelope Encryption

v0.6.0 design target:

- Use WebCrypto for symmetric content encryption.
- Use device identity public keys or a derived conversation key for envelope key wrapping.
- Include `messageId`, `conversationId`, sender, recipient hash, and expiry in associated data.
- Reject decrypt when associated data does not match.
- Sign the canonical envelope before upload and verify the signature before decrypt.
- Reject envelopes for a different `conversationId`, recipient hash, expiry, or sender key.

### ACK Authentication

ACK plaintext:

```ts
export type DeliveryAck = {
  version: 1;
  messageId: string;
  conversationId: string;
  senderDeviceId: string;
  recipientDeviceId: string;
  status: "peer_delivered" | "read";
  at: number;
};
```

ACK must include a signature or MAC over the canonical ACK payload. The router must reject unsigned ACKs for `peer_delivered` and `read`.

## 9. Retry Policy

| Failure | Retry |
| --- | --- |
| P2P connecting timeout | Switch to relay if eligible |
| Relay transient error | Exponential backoff: 1s, 2s, 5s, 15s, 60s |
| Store transient error | Exponential backoff: 5s, 30s, 2m, 10m |
| Provider oversized | Local queue, no remote retry |
| Auth/config missing | Local queue, show setup-required diagnostic |
| Peer decrypt failure | Failed final unless sender can re-encrypt |
| Duplicate provider ACK | Ignore |
| Recipient identity mismatch | Stop remote delivery for that conversation; require recovery |

Retry must stop when:

- user cancels,
- message expires,
- attachment local reference is unavailable,
- route policy changes to direct-only and no P2P is available.
- recipient identity no longer matches the outbox record.

## 12. Migration Plan

1. Existing queued v0.5.0 messages map to `local_queued`.
2. Existing sent/received messages do not need outbox records.
3. Create or repair `recipient_identity` records from existing conversations before creating remote-eligible outbox records.
4. On first v0.6.0 launch, create outbox records only for outgoing messages that are:
   - `queued`,
   - `sending`,
   - `failed` with retryable error,
   - `cancelled` is ignored.
5. If migration cannot resolve recipient identity, keep the message local and show recovery guidance.
6. Migrate global `settings.trustedPeer` into the active or default conversation only when the target conversation can be determined unambiguously. Otherwise keep it as legacy metadata and require re-verification.

## 14. Implementation Order

1. Add `deliveryTypes.ts`.
2. Add `recipientIdentityStore` and migrate trust away from global settings.
3. Replace timestamp-only message/transfer ids with UUID-based ids.
4. Add durable `outboxStore`; in-memory implementation is test-only.
5. Add `deliveryWorker` and ensure it starts on disconnected sends.
6. Wrap current P2P send as `p2pTransport`.
7. Replace `App.handleSendDraft` transport call with `deliveryRouter.send`.
8. Add detailed status to chat store without changing visible UI drastically.
9. Add mock relay/store transports and tests, including token scopes.
10. Add real Ably relay behind env flag.
11. Add Worker/R2 store-forward behind env flag.
12. Add envelope encryption and authenticated ACK.
