# V0.6.0 Hybrid Delivery Requirements

## Goal

Make KunoChat behave like a normal chat app after the first pairing:

- A user opens a conversation and sends immediately.
- The app chooses the fastest safe route without asking the user to press Connect.
- Text should feel instant even while P2P is still connecting.
- Large files should be fastest on the home LAN by using native/direct transfer first.
- Offline-at-home peers should receive queued messages automatically when the peer app opens again.

## Home LAN Priority

The primary production target is home/private-network use. For this profile, speed and ease of use are more important than internet-scale completeness.

Priority order:

1. Same-LAN auto discovery and auto reconnect.
2. Local queued sends that flush automatically when the peer app is reachable.
3. Native direct file transfer for large files.
4. Clear conversation separation so messages never go to the wrong peer.
5. Minimal durable outbox for restart recovery.
6. Cloud relay/store-and-forward only after LAN UX is strong enough to be boringly reliable.

Implications:

- SaaS relay and store-and-forward are not required for the first v0.6 home release.
- Strong cloud-envelope security is deferred until cloud fallback is enabled.
- Basic local trust and recipient matching still remain required because they prevent wrong-device delivery.
- Manual pairing should become a recovery path, not a normal daily action.

## Delivery Model

KunoChat should support four delivery routes, but the first v0.6 home release should actively use P2P direct and local queue only:

1. P2P direct
   - Preferred for ready connections and large files.
   - Uses existing WebRTC/native direct transfer paths.
   - Target: LAN/Tailscale direct file transfer starts within 1.2 seconds when both apps are reachable.

2. Realtime relay
   - Future internet fallback for text, control envelopes, ACKs, and small payloads when P2P is not ready.
   - Not active in the default home LAN profile.
   - Candidate SaaS: Ably or Pusher Channels.

3. Store-and-forward
   - Future internet fallback for peers that are offline outside the home LAN.
   - Not active in the default home LAN profile.
   - Candidate SaaS: Supabase/Firebase for metadata, Cloudflare R2 for encrypted file bodies.

4. Local queue
   - Used when payloads exceed cloud limits, no fallback service is configured, or privacy policy says direct-only.
   - Messages remain visible in the conversation and auto-send when a route appears.

## Route Selection

The first validation implementation lives in `src/features/delivery/deliveryStrategy.ts`.

Default thresholds:

- P2P fallback window: 1200 ms.
- Instant payload threshold: 64 KiB.
- Relay payload max: 100 MiB, internet fallback only.
- Store-and-forward max: 25 MiB, internet fallback only.

Rules:

- If P2P is ready, use P2P.
- In home LAN mode, if LAN discovery can see the peer, prefer reconnecting P2P/native direct before trying any cloud route.
- In home LAN mode, if the peer is unreachable, keep the message local and retry on discovery/reconnect events.
- In internet fallback mode, if the peer is offline and store-and-forward can accept the payload, store remotely.
- In internet fallback mode, if the peer is online and payload is text/control/small, use relay immediately and keep P2P connecting in the background.
- In internet fallback mode, if the peer is online and payload is a large file, give P2P one fallback window before switching to relay.
- If no remote route is available, keep the message in the local queue.

## User Experience

- After first pairing, the normal send path must not show a required Connect button.
- Conversation selection should trigger background reconnection to that peer.
- Sending to a known conversation should trigger route discovery/delivery work even if disconnected.
- Sending while disconnected should create a clock/pending message, not an error.
- The UI should distinguish:
  - local queued,
  - relay accepted,
  - stored for offline delivery,
  - peer delivered,
  - read, if read receipts are enabled later.
- Manual pairing remains available as recovery and new-device setup only.

## Safety Guardrails

Security is secondary for the home LAN profile, but these guardrails remain required because they protect functionality:

- Do not send queued messages to the wrong conversation/peer.
- Keep per-conversation recipient identity so one peer cannot overwrite another peer's trust state.
- Use UUID/random ids so retries and duplicate prevention are reliable.
- Keep cloud credentials and cloud fallback code inactive in the home LAN profile.

When internet fallback is enabled later:

- Relay and store-forward payloads must be encrypted.
- Envelopes and ACKs must be sender-authenticated.
- Provider tokens must be short-lived and scoped; provider secrets must never ship in the desktop app.

## SaaS Candidates

SaaS candidates are for the later internet fallback profile, not the first home LAN priority build.

- Realtime relay: Ably Free or Pusher Sandbox.
- Store metadata: Supabase Free, Firebase Spark, or Neon Free.
- File object fallback: Cloudflare R2 Free.
- Serverless control API: Cloudflare Workers Free.

Official references:

## Acceptance Criteria

- Text sent to a previously paired LAN peer starts reconnect/delivery work within 500 ms.
- Pending text is delivered automatically when the peer app becomes reachable on the same LAN.
- Large files on LAN/Tailscale prefer direct transfer and do not upload to cloud unless direct setup fails.
- Offline text remains in the local outbox for the home LAN profile and is delivered automatically when the peer opens KunoChat on the LAN.
- Offline large files stay local and show a clear pending state in the home LAN profile.
- Duplicate delivery is prevented by stable message ids and idempotent ACK handling.
- Message and transfer ids must be UUID/random-entropy based, not timestamp-only.
- Peer trust is stored per conversation/recipient identity.
- Unit tests cover route selection before service-specific SDKs are introduced.
