# KunoChat v0.4.0 Requirements

## Purpose

v0.4.0 changes KunoChat from a single-peer send pocket into a multi-peer chat handoff app that still feels lightweight. The primary goal is to let the sender choose a target and send immediately, without making the receiver press an approval button every time.

## Background

Current behavior has three UX problems:

- A receiver-side approval step blocks the sender, even when both users already expect the connection.
- Chat history is global, so messages and files from different peers are mixed together.
- Reconnect and peer switching are visible, but the mental model is still "one current peer" instead of "choose who to talk to".

## Goals

- Let the sender initiate a connection by selecting a peer.
- Auto-accept connection requests on the receiving side by default.
- Keep conversations separated by peer.
- Preserve quick local/LAN usage without accounts or cloud relay.
- Keep messages, files, transfer state, unread counts, and notifications associated with the correct peer.
- Keep the UI simple enough for repeated use from a small desktop window.

## Non-Goals

- No account system.
- No cloud-hosted message sync.
- No group chat in v0.4.0.
- No end-to-end identity/signature approval flow revival.
- No mobile client support.
- No multi-device history merge beyond the local app's persisted history.

## Core Concepts

### Peer

A peer is another KunoChat device discovered over LAN/Tailscale or reached through a pairing code.

Required peer fields:

- `peerId`: stable remote device/session identifier when known.
- `displayName`: user-facing name.
- `peerHint`: LAN/Tailscale address hint.
- `source`: `lan` or `tailscale`.
- `platform`: Windows, macOS, Linux, or unknown.
- `fingerprint`: remote identity fingerprint when available.
- `lastSeenAt`: last discovery or connection time.

### Conversation

A conversation is a local thread with exactly one peer.

Required conversation fields:

- `conversationId`: stable local identifier.
- `peerId` or peer fingerprint when known.
- `displayName`.
- `messages`.
- `draftText`.
- `attachments`.
- `unreadCount`.
- `lastMessageAt`.
- `connectionStatus`.

### Active Conversation

Only one conversation can be active in the main chat view at a time. Switching conversations changes the visible message list, draft, attachments, unread state, and target peer.

## Connection Requirements

### Auto-Accept

- When a `connection-request` arrives, the receiver should auto-accept by default.
- The receiver should not show a blocking `Connect / Decline` banner in the normal path.
- The receiver should show a non-blocking notice such as `Atsushi と接続しました`.
- If currently connected to another peer, the app may switch to the new requested peer.
- Switching must update the active conversation to the requester.

### Sender-Initiated Flow

- Sender opens the peer list or pairing screen.
- Sender selects a target peer.
- App sends `connection-request`.
- Receiver auto-accepts.
- Sender connects and can send as soon as WebRTC is ready.

### Manual Pairing Code

- Pairing code remains available as fallback.
- Pairing code should create or activate a conversation for the resolved peer.
- Manual code entry must not be interrupted by auto-connect events.

### Existing Connection

When a new connection request arrives while already connected:

- If the active transfer list is empty, switch automatically.
- If active transfers exist, queue the connection switch until transfers complete or show a compact warning.
- The first v0.4.0 implementation may allow immediate switch, but the risk must be documented in the release notes.

### Reconnect

- Reconnect acts on the active conversation's last known peer endpoint.
- `接続先を選ぶ` opens peer/conversation selection.
- Failed reconnect should keep the user in the same conversation and preserve the draft.

## Chat Separation Requirements

### Message Routing

- Incoming text messages must be appended to the conversation that matches `senderId` or fingerprint.
- Incoming file messages must be appended to the same matched conversation.
- Outgoing messages must be appended only to the active conversation.
- A message from an unknown peer creates a new conversation.

### Conversation List

The main UI needs a peer/conversation selector.

Minimum viable UI:

- A compact conversation switcher accessible from the header.
- Each item shows peer name, platform/source, last message preview, connection status, and unread count.
- Selecting an item switches the active conversation.
- A discovered peer with no messages can appear as a selectable target.

### Unread Counts

- Unread counts are per conversation.
- Global unread count is the sum of all non-active conversations.
- Mini mode red badge shows global unread count.
- Windows taskbar overlay shows global unread count.
- Opening a conversation clears only that conversation's unread count.

### Drafts and Attachments

- Draft text is per conversation.
- Selected attachments are per conversation.
- Switching away and back should preserve unsent text/files.
- Sending while disconnected should either queue locally or show a clear `接続して送信` action. The preferred v0.4.0 behavior is queued send after connection.

## File and Image Requirements

- File transfer state must belong to the conversation where the transfer started.
- Received files/images must preview inside the correct conversation.
- `開く` and `場所` actions must remain available after switching conversations.
- Retry/resume must target the conversation's current peer connection.
- If the peer is disconnected, retry should first reconnect that conversation.

## Notification Requirements

- OS notifications must include the sender/conversation name.
- Clicking/opening from mini mode should route to the conversation with the new message where feasible.
- Red badge count must represent total unread messages across conversations.
- Active conversation messages should not increment unread when the window is focused.

## Settings Requirements

Add settings:

- `接続依頼を自動承認`: default on.
- `転送中は接続先を切り替えない`: default on or documented before implementation.
- `会話履歴を相手別に保持`: always on for v0.4.0; not user-toggleable.

Existing `Forget paired peer` should become peer-scoped:

- Forget current peer.
- Optionally clear all peers/history from a separate destructive action.

## Data Migration Requirements

Current persisted state has a single `messages` array. v0.4.0 must migrate it safely.

Migration rule:

- Create one default conversation from existing messages.
- Use current `settings.peerDisplayName`, saved trusted peer fingerprint, or `Peer` as the conversation label.
- Preserve message order, file metadata, preview URLs, save paths, and transfer states.
- Set `activeConversationId` to the migrated conversation.
- Do not delete existing history during migration.

Storage version should be bumped.

## Implementation Phases

### Phase 1: Data Model

- Introduce `Conversation`, `PeerSummary`, and `activeConversationId`.
- Keep selectors/helpers so existing components can still consume `activeMessages`, `activeDraftText`, and `activeAttachments`.
- Add migration from single-message state.

### Phase 2: Auto-Accept Connection

- Replace blocking request banner with auto-accept behavior.
- Keep a transient notice for visibility.
- Map requester to a conversation before connecting.

### Phase 3: Conversation Selector UI

- Add compact selector from the header.
- Show discovered peers and existing conversations.
- Switch active conversation without losing drafts.

### Phase 4: Routing and Transfers

- Route incoming messages/files by peer.
- Ensure retry/resume/download actions operate on the active or owning conversation.
- Confirm file previews remain available after switching.

### Phase 5: Notifications and Badges

- Make unread counts per conversation and global.
- Route mini mode open to the relevant conversation when possible.
- Keep Windows taskbar red count and mini red count in sync.

## Acceptance Criteria

- Sender selects a discovered peer and connects without receiver approval.
- Receiver sees a non-blocking connected notice.
- Messages from peer A and peer B appear in separate conversations.
- Switching conversations preserves drafts and pending attachments.
- Incoming file/image from peer A appears only under peer A.
- Unread count increments only for non-active conversations.
- Mini mode shows total unread red badge with number.
- Windows taskbar overlay shows total unread number when supported.
- Existing v0.3.x local history migrates into one conversation without data loss.
- `npm run typecheck`, `npm test`, `npm run build`, and release preflight pass.
- Windows installed app verifies version, launch, LAN listener ports, auto-accept request, and conversation separation.
- macOS installed app verifies the same behavior after release.

## Risks

- Immediate peer switching can interrupt active file transfers.
- Peer identity may not be stable across reinstall or key reset.
- Conversation matching by `senderId` alone may split history if session IDs change.
- Persisted migration must avoid losing existing files and messages.
- UI may become too heavy if the conversation selector behaves like a full messenger sidebar.

## Open Decisions

- Should auto-accept be always on, or default on with a Settings toggle?
- Should active file transfers block switching, queue switching, or cancel with warning?
- Should a peer be matched primarily by fingerprint, `senderId`, or endpoint hint?
- Should sender-side messages queue while connecting, or require connection before pressing Send?
- Should discovered peers with no history appear in the same list as conversations or in a separate `Nearby` section?
